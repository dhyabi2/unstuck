# unstuck — code audit, 2026-10-05

First audit of this repository. Scope: the tree at `2af1169` (`main`). Lens: can an agent get
paid in XNO through this, today, without being hurt?

`unstuck` is listed in Tier 0 group 3 as "the agent network: asks, answers and settlements in
XNO". This run followed one question down: when an agent pays this network, what number does
the network read as the payment?

## Found and fixed — a floor payment bought any price, and a full payment was refused

`opener/bridge.js:137` and `opener/nano-bridge-persist.js:183` both computed the amount a
payment moved like this:

```js
const amount = BigInt(block.balance) - BigInt(info.previous_balance || "0");
```

Two things are wrong with that line, and they compound:

1. a `block_info` answer has **no `previous_balance` field**, so `|| "0"` always won and the
   subtraction was a no-op;
2. `contents.balance` on a state block is the **payer's balance after the send**, not the
   amount sent.

So `amount` was the payer's leftover balance. `verifyNanoPayment` is the gate `/verify-payment`
uses to decide whether a payment covers the price, and both directions of the comparison were
wrong:

```
payer holds 100 XNO, sends the 0.000001 XNO floor
  amount read as 99.999999 XNO  ->  ACCEPTED against a price of 1 XNO
  (a payment of a millionth of the price buys the call)

payer sends 1 XNO, emptying the account
  balance after is 0, amount read as 0  ->  REFUSED as "zero or negative amount"
  (a payment that really happened does not pay)
```

The first is the one that costs us: anyone holding a balance paid the floor and got whatever
they asked for. The second costs the payer: an agent that spends its last XNO is told it did
not pay. In `nano-bridge-persist.js` the same number is also what `savePayment` writes into the
`payments` table, so the stored record of what an agent paid was the balance it kept.

**Fixed** by reading the amount the node reports for the block — `block_info`'s own top-level
`amount` — and refusing rather than guessing when it is absent, plus `subtype === "send"` so a
block that moved value the other way cannot be presented as a payment.

Proved both directions. With the production fix reverted and the new tests kept, 5 laws fail:

```
FAIL B3 a floor payment out of a full account does not cover a 1 XNO price:
     a payment of 1000000000000000000000000 raw was accepted against a price of
     1000000000000000000000000000000 raw
FAIL B3 a payment that empties the payer's account still pays: refused as: zero or negative amount
FAIL B3 the amount reported back is the amount the block moved:
     + '7000000000000000000000000000000'   (what the payer kept)
     - '3000000000000000000000000000000'   (what the payer sent)
FAIL B3 a block that is not a send is refused
FAIL B3 a node that reports no amount is refused rather than guessed at
```

With the fix, all 13 laws pass.

## Found and fixed — four of the six laws in this suite could not fail

`opener/test_bridge.js` ran each law as:

```js
const law = (n, fn) => {
  try { fn(); console.log(`ok   ${n}`); }
  catch (e) { failed++; console.log(`FAIL ${n}: ${e.message}`); }
};
```

`fn()` returns a promise for an `async` law, and a rejected promise is not something `catch`
can see — the law had already printed `ok` and returned. Four of the six laws were `async`,
including the whole of B3 (on-chain verification) and B4 (idempotency). That is why the defect
above shipped: the suite covering it reported `ok` whatever it asserted.

The laws are now collected and awaited one at a time. That alone turned up a second wrong
assertion: `B3 verifyNanoPayment rejects non-state blocks` fed the RPC an `error` answer, which
`nanoRpc` **throws** on, so it never reached the `block.type !== "state"` branch it is named
for. It now feeds a real answer carrying a non-state block, and the throwing path is pinned in
a law of its own that says what actually happens (`/verify-payment` answers 400 with the node's
message, not 402 `verified: false`) rather than asserting the opposite of it.

## Checked and clean

- **No secret in the tree.** No seed, private key or mnemonic in any tracked file, and no
  `.env`/credential file is tracked. Every bare 64-hex string in the code is a block hash or a
  public key — `opener/reply-sara-7.js:34` and `reply-sara-8.js` are the starter send's block
  hash, `resume_waiting.py:114` is a block hash quoted in outreach prose, and the hex in
  `test_nano_keygen.py` / `test_nano_receive.py` are known-answer vectors.
- **The on-chain destination check is right.** `link_as_account !== NANO_ADDRESS` refuses a
  send to anyone else, and the new `B3 a send to somebody else is refused` law passes both
  before and after this change — the one part of the verification that was already sound.
- **Idempotency.** `/verify-payment` keys on `block_hash` and answers `already_processed` for a
  repeat, so one block cannot be spent twice against the bridge (law B4).
- **`site/agent.json`** is the network's entry point for an agent and it is accurate and
  thorough: the XNO-only settlement claim, the payment address, the `api_path` note about the
  API never sitting at the origin root, and the `first_call` on-ramp explanation of why an
  agent cannot open its own Nano account.

## Found, not fixed — reported instead

- **`float` on a quoted amount.** `opener/bridge.js:118`
  `BigInt(Math.floor(nanoAmount * 1e30))` carries an XNO amount through a double. The quote it
  derives from is already a floating CoinGecko price, so the ~16th-digit loss changes no
  decision — but if the price feed ever answers `0`, `usdNum / price` is `Infinity`,
  `Math.floor(Infinity)` is `Infinity`, and `BigInt(Infinity)` throws a `RangeError` out of
  `usdToNanoRaw` instead of refusing the quote. Left alone because repairing it properly means
  deciding how the bridge should price when the feed is unusable, which is a judgement about
  the product, not about reading JSON.
- **No `README` at the repository root.** `git ls-files` matches none. An agent is served by
  `site/agent.json`, which is good, but a person who clones this finds 57k lines of `AGENTS.md`
  and no quickstart. Writing one is new content rather than a fix, so it is recorded here.
- **Two tests fail on `main` and still fail, unrelated to this change.**
  `opener/test_bridge_server.js` spawns `node opener/bridge.js` with `cwd: process.cwd()`, so it
  only works when run from the repository root (`ECONNREFUSED` otherwise); from the root it is
  4/4 green with this change. `opener/test_nano_onramp_check.js` is 3 FAILURES before and after
  — it needs a live scratch network this environment cannot reach.

## Could not verify

- **Against a real Nano node.** No socket was opened. The `block_info` answers the new laws use
  are written to the node RPC's documented shape (`amount`, `balance`, `subtype`, `confirmed`,
  `contents`), not captured from a live node — this environment's network policy does not reach
  one. The field this fix reads, top-level `amount`, is the thing to confirm from a connected
  box; that `contents.balance` is the post-send balance does not depend on it.
- **Whether `/verify-payment` is reachable in production.** The deployed API is
  `getunstuck.space/unstuck/api`; whether the bridge on port 3402 is exposed behind it was not
  established, so how often this fired in practice is unknown. It does not change the defect.
- **Confirmation.** `verifyNanoPayment` does not require `info.confirmed === "true"`, so an
  unconfirmed send — which its own payer can still fork away — is accepted. That is a separate
  concern from which field the amount is read from and is not carried on this branch.
- **The rest of the tree.** `swarm-tools/`, `site/tests/` and the ~90 one-off scripts under
  `opener/` were not read end to end; this run went down the payment-verification path only.
