# unstuck — code audit, 2026-10-09

Scope: can an agent get paid in XNO through this network, today, without being hurt.
Audited on `main`, the repository's default branch — what every clone and every
directory listing of this public repository shows.

## Checked

- `opener/network-settle.js` — the on-chain bounty verifier, read line by line.
- `opener/network-store.js` — `recordSettlement`, `getStanding`, the settlement columns.
- `opener/nserver-persist.js` — `POST /ask/:id/settle`, `GET /standing`, and the
  order in which they establish authority.
- `opener/test_network_settle.js` — the laws the repository asserts about settlement.
- All 28 `opener/test_*.js` suites, on `main` and on this branch, for comparison.

## Found

**`POST /ask/:id/settle` recorded any 64-hex string as a verified on-chain
settlement, and the answerer's standing went up (dhyabi2/unstuck#14, filed
2026-10-03, still open on this branch today).**

`opener/nserver-persist.js:242` `handleSettle` called
`s.recordSettlement(...)` and nothing else. `opener/network-store.js:398`
`recordSettlement` checked the asker's identity, the ask's accept token, the
status, the absence of an earlier settlement, and that the hash was 64 hex
characters — then wrote `settlement_block` **and `settlement_verified_at`**.
No node was ever asked.

`opener/network-settle.js` has exported `verifyBlockPayment` the whole time, and
`network-store.js:386-390` said in as many words that callers "should verify it
against the Nano ledger (verifyBlockPayment) before recording". **No caller
did.** A documented step with no implementation reads exactly like a step that
happened.

Reproduced against this tree, with the ask's own valid accept token:

```
POST /ask/1/settle  paymentBlock=DDDDDDDDDDDDDDDD...  ->  HTTP 200
   {"ok":true,"settlementBlock":"DDDD…DDDD","settledAt":"2026-10-09T00:55:40.357Z"}
   settlementBlock      = DDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDDD
   settlementVerifiedAt = 2026-10-09T00:55:40.357Z
   standing[answerer]   = 1
```

`getStanding()` counts any ask with a non-null `settlement_block`, so that row
is standing an answerer never earned — and the network's published claim is
on-chain settlement.

**The test suite certified it.** `opener/test_network_settle.js` sent
`paymentBlock: "D".repeat(64)` and asserted `L13 settle via HTTP 200`, and its
own method note said "mock no RPC (settlement recording is local, the block hash
is the proof the caller verified)". Nothing verified it. 22 checks, all green,
all passing on a defect.

Two further gaps in the verifier itself, found while reading it:

- **No `confirmed` check** (`network-settle.js:52-55` went straight from
  existence to the link). An unconfirmed block can still be forked away.
- **No `subtype` check.** `link_as_account` is populated on a receive too —
  there it is the source block's *hash* read as an account, a well-formed
  `nano_` address belonging to nobody. The node names the direction; it was not
  being asked.

And in the store: **nothing stopped one block from settling many asks.** A send
covers the one bounty it was sent for, and standing is distinct askers over
settled asks, so the same hash on a second ask buys standing twice.

## Fixed

On branch `fix/settle-records-any-hash`, refusals only — nothing this change
makes acceptable was refused before:

- `nserver-persist.js` — `handleSettle` now prechecks authority against the
  store, reads the block off a node, and records only on a valid verification.
  Authority first, deliberately: a caller holding no accept token cannot make
  this server talk to a node at all (covered by a test that counts RPC calls).
- `network-store.js` — the authority and state checks are factored into
  `settlementPrecheck`, which the handler and `recordSettlement` both run, so
  the two cannot drift. `recordSettlement` refuses without
  `verification.valid === true`, refuses a verification carrying no evidence,
  refuses one whose evidence names a different block, and refuses a hash that
  already settles another ask.
- `network-settle.js` — refuses an unconfirmed block, refuses anything the node
  does not call a `send`, and returns the `evidence` it read so a stranger can
  re-derive the verdict from `block_info` rather than trust us.

`opener/test_network_settle.js` now mocks a node and states the law as **L16**.
**50 checks pass, up from 22.**

Failing-then-passing, each half proved separately:

| mutation | result |
| --- | --- |
| production reverted to `main`, tests kept | the ghost-block, no-verification and wrong-block tests fail |
| only `handleSettle` reverted | 3 fail — the store refuses everything, so nothing can settle at all |
| the full fix | 50 pass |

`node repro14.js` against `origin/main` returns HTTP 200 and standing 1; against
this branch, HTTP 400 `block does not prove this payment: could not fetch block:
Block not found`, `settlementBlock = null`, standing unset.

## Could not verify

- **The two fake rows already on the live network** (asks 585 and 544, cited in
  #14) are rows in the deployed database, not in this tree. This change stops
  new ones; it cannot clear those. They are the owner's or the box's to delete.
- **Whether anything outside this repository calls `recordSettlement` directly.**
  The only caller here is the HTTP handler. A direct caller elsewhere now fails
  closed, which is the intended direction, but an operator should know it.
- **Six `opener/test_*.js` suites fail on this branch and fail identically on
  `main`** — `test_bridge_invite`, `test_bridge_server` (wants a server on
  :3999), `test_nano_onramp_check`, `test_onramp` (wants a wallet file),
  `test_opening` (wants a live database), `test_room_bridge` (wants
  `/root/unstuck/opener/unstuck-bridge.js`). All six want the box, not a
  checkout. Not touched by this change and not investigated further.
- **`main` and `master` have unrelated histories and are diverging in both
  directions.** `master` carries an equivalent settle fix (PRs #19-#22) that
  `main` never received; `main` carries #23 and #24 that `master` did not. This
  branch fixes `main`, the default branch, on its own terms. The split itself is
  a repository setting and is not a routine's to change.
