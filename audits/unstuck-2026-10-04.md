# unstuck — code audit, 2026-10-04

Scope: the XNO payment path only — can an agent get paid in XNO through this
network, today, without being hurt. `opener/network-store.js`,
`opener/network-settle.js`, `opener/nserver-persist.js` (`POST /ask/:id/settle`,
`GET /standing`), read end to end against `dhyabi2/unstuck#14`.

Branch: `master` at `92dfa9a` (the repository's live trunk; `main` is an
unrelated 2026-09-24 snapshot and is not what this audits).

## Checked

- `recordSettlement` and every refusal it gives.
- `verifyBlockPayment` against each field of a real `block_info` answer.
- `handleSettle`, and the order its refusals run in.
- `getStanding`, and what a settled row buys.
- The whole `opener/test_*.js` set, before and after: 30 files, 20 pass, 10 fail
  for want of `node_modules` (`better-sqlite3`, `nanocurrency`) in this sandbox —
  **the same 10, identically, on `master` and on the fix branch.**

## Found

**1. A settlement was recorded without ever asking a node — `unstuck#14`, confirmed.**
`opener/nserver-persist.js:248` called `s.recordSettlement(id, body.paymentBlock,
body.accept_token)` and `recordSettlement` (`opener/network-store.js:393`)
checked only that the ask was `paid`, unsettled, that the hash was 64 hex
characters, and that the caller held the accept token. It then wrote
`settlement_block` **and `settlement_verified_at`**. Nothing asked whether the
block existed, was confirmed, was a send, came from the asker, reached the
accepted answerer, or carried the bounty. `getStanding`
(`network-store.js:425`) counts distinct askers over settled rows, so an
unverified settle bought standing. The verifier for exactly this,
`network-settle.verifyBlockPayment`, has been in the repository since block 16
and was never called from any code path — only from the test file.

**2. The three settlement laws asserted the wrong thing.** L12 read "records a
64-hex settlement block for a paid ask" — a statement the defect satisfies.
`test_network_settle.js` settled with `"A".repeat(64)` and `"D".repeat(64)` and
called it a pass; its own method note said "mock no RPC (settlement recording is
local, the block hash is the proof the caller verified)", which was the premise
that was wrong.

**3. `verifyBlockPayment` would have accepted two kinds of block that prove nothing.**
No confirmation check: an unconfirmed block can still be forked away. And the
send test was `link_as_account` being a `nano_` address — true of a *receive*
too, where `link` is the source block's hash and `link_as_account` is that hash
re-read as an account. The node names the direction in `subtype` and it was not
read.

**4. The sender check had never once run.** `verifyBlockPayment` reads
`info.block_account`; the test's RPC stub set `account`. The branch
`expected.fromAddress && info.block_account` was therefore always skipped, and a
green L14 said nothing about it.

**5. One block could settle any number of asks.** Nothing compared a hash
against the settlements already recorded, so one send could be presented for
every open ask of the same answerer and buy standing from each.

## Fixed

On `fix/settle-verifies-the-block-on-chain`, all refusals, nothing widened:

- `verifyBlockPayment` refuses an unconfirmed block and anything the node does
  not call a `send`; unprovable counts as no, both ways.
- `settlementPrecheck` (new, in the store) holds every refusal that needs no
  node, including the new one-block-one-ask rule, and returns the asker,
  answerer and bounty the chain must show. `recordSettlement` runs it and then
  **requires** a `{valid: true}` verification — `settlement_verified_at` names a
  verification and there is now no writing it without one.
- `handleSettle` runs the precheck, then verifies against the node, then
  records. An unreachable node is a refusal, not a 200.
- L12, L13 and L14 amended in `LEDGER.md` to state what they now prove.

Evidence: 47 checks pass. Reverting each of the three production files alone
fails 3, 9 and 9 of them respectively. The issue's own reproduction — settling
with the hash of an unrelated smaller send between two other accounts — is a
test, and so are a hash of nothing, a send under the bounty, an unconfirmed
send, a receive, a wrong sender, a reused block (either hex case) and a node
that is down.

## Could not verify

- **The two fake rows on the live network are still there.** Asks 585 and 544
  carry `settlement_block` values starting `abcdef0123456789` and
  `AAAAAAAAAAAAAAAA` with a verified-at time. Neither is a block. This fix stops
  new ones; it does not clear those, and clearing rows in the live database is
  not a cloud session's to do. It is the one thing in this audit that needs a
  person.
- **10 of the 30 `opener/test_*.js` files cannot run here** for want of
  `node_modules`. They fail identically on `master`, so this change did not
  break them, but they were not a check on it either.
- **No real node was called.** The RPC is stubbed with a small fake chain shaped
  like a `block_info` answer (upper-case hashes, string `confirmed`, explicit
  `subtype`). The field names are read off the live code path, not off a node
  this session talked to.
